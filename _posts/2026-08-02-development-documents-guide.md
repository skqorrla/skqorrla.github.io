프로젝트를 시작하면 늘 같은 질문에 부딪힙니다. "문서를 어디까지 써야 하지?" 안 쓰면 3개월 뒤에 내가 왜 이렇게 짰는지 기억이 안 나고, 다 쓰자니 코드보다 문서 쓰는 시간이 더 길어집니다. 게다가 애써 쓴 문서는 대부분 금방 낡습니다.

이 글에서는 실무에서 쓰이는 개발 문서를 **프로젝트 단계별로 지도처럼 펼쳐놓고**, 각 문서가 **언제 / 누가 / 무엇을 담아야 하고 / 왜 필요한지**를 정리합니다. 마지막에는 프로젝트 규모별로 "이건 꼭 쓰고, 이건 건너뛰어도 된다"는 최소 세트와, 문서가 썩지 않게 유지하는 방법까지 다룹니다.

## 1. 개발 문서는 왜 필요한가

문서의 진짜 독자는 지금의 내가 아니라 **6개월 뒤의 나와, 다음 주에 합류할 동료**입니다. 그 관점에서 보면 개발 문서는 크게 세 가지 역할을 합니다.

1. **의사결정의 기록** — "왜 MySQL 대신 PostgreSQL을 골랐나?" 코드는 결과만 보여줄 뿐 이유를 말해주지 않습니다. 이유가 사라지면 후임자는 같은 논의를 처음부터 다시 하거나, 이미 검토해서 기각한 선택지를 다시 채택합니다.
2. **인터페이스 계약** — API 명세, 데이터 모델, 요구사항 문서는 팀과 팀 사이의 계약서입니다. 계약이 문서로 없으면 통합 시점에 "나는 이렇게 알고 있었는데"가 터집니다.
3. **운영 매뉴얼** — 새벽 3시에 알림을 받은 당직자가 볼 문서입니다. 이때는 "잘 아는 사람"이 아니라 "문서"가 대응 속도를 결정합니다.

그런데 문서에는 명백한 비용이 있습니다. 가장 큰 비용은 작성 시간이 아니라 **문서 부패(documentation rot)** 입니다. 코드는 깨지면 빌드가 실패하거나 테스트가 빨간불을 켜지만, 문서는 **아무 소리 없이 조용히 틀려집니다.** 한 연구에서는 문서 품질 문제 중 39%가 "최신성 문제"였다고 보고합니다.

그래서 목표는 "문서를 많이 쓰는 것"이 아니라 **"틀리면 손해가 큰 것만, 그게 결정되는 시점에 쓰는 것"** 입니다. 아래의 문서들도 전부 쓰라는 목록이 아니라, 필요할 때 골라 쓰는 메뉴판으로 봐주세요.

## 2. 프로젝트 단계별 문서 지도

![프로젝트 단계별 개발 문서 지도](/assets/images/docs-map.jpeg)

*기획부터 운영까지, 각 단계에서 결정이 굳는 시점에 필요한 문서들. 왼쪽으로 갈수록 "무엇을 왜 만드는가"에 답하고, 오른쪽으로 갈수록 "어떻게 굴리는가"에 답합니다. 문서가 가장 많이 몰리는 구간은 설계 단계입니다.*

| 단계 | 대표 문서 | 답하는 질문 |
|---|---|---|
| 기획 | PRD, SRS(요구사항 명세) | 무엇을, 왜 만드는가 |
| 설계 | 기술 설계 문서, RFC, ADR, API 명세, ERD | 어떻게 만드는가 |
| 구현 | README, CONTRIBUTING, 코딩 컨벤션, Issue·PR 템플릿 | 어떻게 참여하는가 |
| 검증 | 테스트 계획서, 테스트 케이스, 릴리스 체크리스트 | 다 됐다는 걸 어떻게 확인하는가 |
| 배포·운영 | CHANGELOG, 릴리스 노트, 런북, 장애 회고 | 어떻게 굴리고 고치는가 |
| 사용자 | 튜토리얼, How-to, 레퍼런스, 설명 문서 | 사용자가 어떻게 쓰는가 |

핵심은 **문서마다 "결정이 굳는 시점"이 다르다**는 것입니다. 요구사항이 흔들리는 동안 쓴 설계 문서는 버려지고, 이미 다 만들고 나서 쓴 ADR은 회고문이 될 뿐 의사결정에 아무 영향을 주지 못합니다.

## 3. 기획 단계 — 무엇을 왜 만드는가

### 3-1. PRD (Product Requirements Document, 제품 요구사항 문서)

**작성 시점** — 개발 착수 전, 기능 아이디어가 "만들기로 결정"된 직후.
**주 작성자** — PM/기획자 (개발·디자인·QA가 리뷰).

**담을 내용**

- 배경과 문제 정의: 어떤 사용자가 무엇 때문에 불편한가
- 목표와 성공 지표: 무엇이 얼마나 개선되면 성공인가 (예: 가입 이탈률 30% → 20%)
- 사용자 스토리 / 유스케이스: "OO로서 OO를 하고 싶다"
- 기능 요구사항 목록과 우선순위 (Must / Should / Could)
- **범위 밖(Out of Scope)**: 이번에 하지 않는 것
- 화면 흐름·와이어프레임 링크, 오픈 이슈

**왜 필요한가** — PRD는 **"사용자 관점에서 무엇을"** 을 정의하는 문서입니다. 여기서 가장 값어치 있는 항목은 의외로 목표 지표와 *범위 밖* 항목입니다. 범위를 명시적으로 잘라두지 않으면 개발 중반에 "이것도 되면 좋잖아요"가 무한히 들어오는 스코프 크리프(scope creep)를 막을 방법이 없습니다.

### 3-2. SRS (Software Requirements Specification, 소프트웨어 요구사항 명세서)

**작성 시점** — PRD 확정 후, 설계 착수 전.
**주 작성자** — 시스템 분석가 / 테크리드 (QA가 함께 검증).

**담을 내용**

- 기능 요구사항: 시스템이 수행해야 할 동작을 **검증 가능한 문장**으로
- 비기능 요구사항: 성능(응답시간, TPS), 가용성, 보안, 확장성, 접근성, 규제 준수
- 외부 인터페이스: 연동 시스템, 프로토콜, 데이터 포맷
- 제약 조건과 가정, 용어 정의(Glossary)

**왜 필요한가** — PRD가 "사용자가 원하는 것"이라면 SRS는 **"시스템이 해야 하는 것"** 입니다. 특히 비기능 요구사항은 SRS에 적히지 않으면 아무도 책임지지 않다가 성능 테스트에서 터집니다. 또 SRS의 각 항목은 그대로 **테스트 케이스의 근거**가 되므로, "검증할 수 없는 문장"(예: "빨라야 한다")은 요구사항이 아닙니다. "95 백분위 응답시간 300ms 이하"처럼 숫자로 적어야 합니다.

### 3-3. 요구사항 문서 4형제 정리

이름이 비슷해서 가장 많이 헷갈리는 부분입니다.

| 문서 | 관점 | 답하는 질문 | 주 독자 |
|---|---|---|---|
| BRD (비즈니스 요구사항) | 사업 | 왜 이 사업을 하는가 | 경영진, 이해관계자 |
| PRD (제품 요구사항) | 사용자 | 사용자에게 무엇을 제공하는가 | 개발, 디자인, QA |
| SRS (소프트웨어 요구사항) | 시스템 | 시스템이 무엇을 해야 하는가 | 개발, QA |
| TRD (기술 요구사항) | 기술 | 어떤 기술로 구현하는가 | 개발, 인프라 |

실무에서는 이 넷을 다 쓰는 조직이 드뭅니다. **소규모 팀이라면 PRD 하나에 비기능 요구사항 절을 추가해서 SRS 역할까지 겸하게 하는 것**이 현실적입니다.

## 4. 설계 단계 — 어떻게 만드는가

여기가 문서 종류가 가장 많이 갈리는 구간입니다. Design Doc, RFC, ADR은 셋 다 "기술적 결정을 적는 문서"라서 자주 혼용되는데, **분량과 목적이 다릅니다.**

### 4-1. 기술 설계 문서 (Technical Design Doc)

**작성 시점** — 요구사항 확정 후 ~ 코딩 시작 전. 규모가 큰 기능일수록 필수.
**주 작성자** — 해당 기능을 구현할 개발자 본인.

**담을 내용**

- 문제 정의와 목표 / 비목표(Non-goals)
- 제안하는 아키텍처: 컴포넌트 구성도, 데이터 흐름
- 상세 설계: 주요 클래스·모듈, 데이터 모델 변경, API 변경
- **검토했지만 채택하지 않은 대안과 그 이유**
- 위험 요소, 마이그레이션 계획, 롤백 전략
- 테스트 전략, 예상 일정, 미해결 질문

**왜 필요한가** — 설계 문서의 가장 큰 효용은 **"쓰는 과정에서 설계가 검증된다"** 는 점입니다. 머릿속으로는 매끄럽던 설계가 글로 쓰는 순간 "이 경우엔 어떻게 되지?"가 드러납니다. 문서 한 장 쓰는 데 하루가 들어도, 잘못된 구조로 2주 짜고 갈아엎는 것보다 압도적으로 쌉니다. 또한 리뷰어가 **코드 리뷰 단계가 아니라 설계 단계에서** 문제를 지적할 수 있게 해줍니다. 코드 리뷰에서 "구조를 바꾸자"는 지적은 사실상 재작업 통보이지만, 설계 리뷰에서는 댓글 한 줄입니다.

### 4-2. RFC (Request for Comments)

**작성 시점** — 여러 팀에 영향을 주는 결정을 내리기 전, **합의를 모아야 할 때**.
**주 작성자** — 제안자 (모든 관련자가 코멘트로 참여).

**담을 내용** — 설계 문서와 구조는 비슷하지만, 다음이 추가됩니다.

- 제안 상태(Draft / In Review / Accepted / Rejected)
- 승인자(Approver) 목록과 서명·반대 의견
- 코멘트 마감 기한
- 다른 팀에 미치는 영향과 필요한 협조

**왜 필요한가** — RFC는 문서라기보다 **비동기 의사결정 프로세스**입니다. 회의실에 10명을 모으는 대신 문서에 코멘트를 달게 해서, 시간대가 다르거나 그 자리에 없던 사람도 논의에 참여하고 그 논의가 **기록으로 남게** 만듭니다. Stripe, Cloudflare 등 여러 회사가 이 방식을 표준 프로세스로 씁니다. 반대로 팀이 5명이고 다 같은 방에 있다면 RFC는 과합니다.

### 4-3. ADR (Architecture Decision Record, 아키텍처 결정 기록)

**작성 시점** — 되돌리기 어려운 구조적 결정을 **내린 직후**. (데이터베이스 선택, 인증 방식, 메시지 큐 도입, 모놀리스 분리 등)
**주 작성자** — 결정에 참여한 개발자.

Michael Nygard가 2011년에 제안한 고전적인 템플릿은 다음과 같습니다.

```markdown
# ADR-0007: 세션 저장소로 Redis를 채택한다

## Status
Accepted (2026-08-02)

## Context
- 현재 세션을 서버 메모리에 저장하고 있어 스케일 아웃 시 로그인이 풀린다.
- 배포마다 전 사용자가 로그아웃되는 문제가 월 4회 발생 중.
- 후보: (a) Sticky Session, (b) DB 세션 테이블, (c) Redis

## Decision
Redis를 세션 저장소로 채택한다. 인프라팀이 이미 Redis 클러스터를
운영 중이라 추가 운영 부담이 없고, TTL 기반 만료가 기본 제공된다.

## Consequences
- (+) 무중단 배포·스케일 아웃 시 세션이 유지된다.
- (+) 세션 만료 로직을 직접 구현할 필요가 없다.
- (−) Redis가 단일 장애점이 된다. → 센티널 구성 필요(ADR-0009에서 다룸)
- (−) 로컬 개발 환경에 Redis 의존성이 추가된다.
```

**핵심 규칙 3가지**

- **1페이지를 넘기지 않는다.** 길어진다면 결정을 여러 개 섞어 쓰고 있거나, 구현 상세를 넣고 있는 것입니다.
- **상태(Status)를 관리한다.** `Proposed` → `Accepted` → `Deprecated` / `Superseded`. 결정이 뒤집히면 **기존 ADR을 수정하지 않고**, 새 ADR을 쓴 뒤 옛 문서를 `Superseded by ADR-0012`로 표시합니다.
- **코드와 같은 저장소에 둔다.** `docs/adr/0007-redis-session-store.md` 처럼 두고 PR에 포함시키면, 결정과 코드가 같은 리뷰 흐름을 탑니다.

**왜 필요한가** — ADR은 **"왜 이렇게 되어 있는가"에 대한 시간순 로그**입니다. 신규 입사자가 "이거 왜 이렇게 짰지, 바꿔야겠다"고 생각할 때 ADR을 읽고 "아, 이런 제약 때문이었구나"를 알게 되는 것 — 이게 ADR의 전부이자 핵심 가치입니다. 반대로 결정을 **되돌릴 때** 어떤 전제가 더 이상 유효하지 않은지 확인하는 근거도 됩니다.

> 참고로 `In the context of <상황>, facing <문제>, we decided for <선택지> to achieve <목표>, accepting <감수할 단점>` 형태의 **Y-statement** 한 문장 포맷도 있습니다. 팀이 문서를 부담스러워하면 이 한 줄부터 시작해도 충분합니다.

### 4-4. Design Doc vs RFC vs ADR 한눈에

![Design Doc, RFC, ADR의 작성 시점과 수명 비교](/assets/images/design-rfc-adr-lifespan.jpeg)

*세 문서의 결정적 차이는 내용이 아니라 수명입니다. RFC(초록)는 결정이 내려지는 순간 역할이 끝나고, 설계 문서(파랑)는 구현이 배포되면 수명을 다합니다. ADR(주황)만 화살표로 오른쪽 끝까지 이어집니다 — 몇 년 뒤 "이거 왜 이렇게 되어 있지?"라고 묻는 사람이 읽을 유일한 문서이기 때문입니다.*

| 구분 | 설계 문서 | RFC | ADR |
|---|---|---|---|
| 목적 | 어떻게 만들지 설계 | 합의 도출 | 결정 이유 보존 |
| 시점 | 구현 직전 | 결정 전 | 결정 직후 |
| 분량 | 수 페이지 | 수 페이지 | 1페이지 |
| 수명 | 구현되면 역할 종료 | 결정되면 종료 | **영구 보존** |
| 수정 | 자유롭게 갱신 | 논의 중 갱신 | **불변, 새 문서로 대체** |
| 범위 | 기능 하나 | 조직 전반 | 결정 하나 |

셋 중 하나만 골라야 한다면 **ADR을 추천**합니다. 가장 짧고, 가장 오래 살아남고, 없을 때 손해가 가장 큽니다.

### 4-5. API 명세 (OpenAPI / Swagger)

**작성 시점** — 프론트엔드와 백엔드가 **병렬로 개발을 시작하기 전.** 즉 구현보다 먼저.
**주 작성자** — API를 제공하는 쪽 개발자.

**담을 내용**

- 엔드포인트, HTTP 메서드, 경로·쿼리·바디 파라미터
- 요청·응답 스키마와 **실제 예시 값**
- 인증 방식 (Bearer, API Key, OAuth 등)
- **에러 응답과 에러 코드 표** — 실무에서 가장 자주 빠지고, 가장 자주 문의가 들어오는 부분
- 페이징·정렬·필터 규칙, Rate Limit, 버전 정책

**왜 필요한가** — API 명세는 프론트/백 사이의 **계약서**입니다. 명세가 먼저 있으면 프론트엔드는 목(mock) 서버로 백엔드를 기다리지 않고 개발할 수 있습니다. 그리고 OpenAPI 형식으로 쓰면 문서가 **문서로만 남지 않습니다.** 코드 생성(클라이언트 SDK), 목 서버, 계약 테스트, API 게이트웨이 설정까지 같은 파일 하나에서 파생시킬 수 있어, "문서와 실제 API가 다른" 최악의 상황을 구조적으로 막습니다.

### 4-6. 데이터 모델 문서 / ERD

**작성 시점** — 설계 단계, 첫 마이그레이션 작성 전.

**담을 내용** — 엔티티와 관계(ERD 다이어그램), 테이블별 컬럼 정의와 제약조건, 인덱스 전략과 그 이유, 주요 조회 패턴, 데이터 보존·삭제 정책(개인정보 포함 여부).

**왜 필요한가** — 스키마는 **가장 바꾸기 어려운 결정**입니다. 코드는 리팩터링하면 되지만 운영 중인 테이블 구조는 마이그레이션·다운타임·데이터 정합성 문제를 동반합니다. 특히 "이 컬럼은 왜 nullable인가", "왜 정규화하지 않았는가" 같은 판단은 ERD 그림만으로는 전달되지 않으므로 **문장으로 함께 남겨야** 합니다.

## 5. 구현 단계 — 어떻게 참여하는가

### 5-1. README

**작성 시점** — 저장소를 만든 **첫날**. (완성 후가 아닙니다)

**담을 내용**

- 이 프로젝트가 무엇이고 어떤 문제를 푸는지 (3줄 이내)
- 기술 스택과 아키텍처 요약
- **로컬 실행 방법**: 사전 요구사항 → 설치 → 환경변수 → 실행 → 확인
- 테스트 실행 방법, 빌드·배포 방법
- 디렉터리 구조 설명, 관련 문서 링크

**왜 필요한가** — README의 성공 기준은 하나입니다. **"신규 합류자가 아무에게도 묻지 않고 로컬에서 앱을 띄울 수 있는가."** 이 기준을 통과하지 못하는 README는 온보딩 때마다 선배 개발자의 반나절을 소모시킵니다. 가장 좋은 검증 방법은 새로 합류한 사람에게 README만 보고 세팅하게 하고, **막힌 지점을 그 사람이 직접 PR로 고치게 하는 것**입니다.

### 5-2. CONTRIBUTING / 코딩 컨벤션

**작성 시점** — 팀원이 2명 이상이 되는 순간.

**담을 내용** — 브랜치 네이밍과 커밋 메시지 규칙, PR 크기·리뷰 기준, 코드 스타일(가능하면 문장 대신 **린터·포매터 설정 파일**로), 네이밍 컨벤션, 테스트 작성 기준, 로컬 개발 워크플로.

**왜 필요한가** — 컨벤션 문서의 목적은 **코드 리뷰에서 취향 논쟁을 없애는 것**입니다. 들여쓰기와 따옴표를 두고 매번 리뷰가 붙으면 정작 로직 리뷰에 쓸 집중력이 남지 않습니다. 다만 **기계가 강제할 수 있는 것은 문서가 아니라 도구에 넣으세요.** 포매터가 자동으로 고쳐주는 규칙을 문서에 적는 것은 낭비이고, 곧 문서와 설정이 어긋납니다. 문서에는 자동화할 수 없는 것 — 이름 짓는 원칙, 예외 처리 방침, 계층 간 의존 규칙 — 만 남깁니다.

### 5-3. Issue·PR 템플릿

**작성 시점** — 협업 시작 시점. `.github/ISSUE_TEMPLATE/`, `.github/pull_request_template.md`에 둡니다.

**왜 필요한가** — 템플릿은 **문서 중에서 유일하게 "읽히지 않아도 효과가 있는" 문서**입니다. 아무도 가이드를 읽지 않아도, 이슈 작성 창에 재현 절차·기대 동작·실제 동작 칸이 미리 떠 있으면 입력 품질이 올라갑니다. 브랜치 전략과 PR 관리에 대한 자세한 내용은 [이전 글]({% post_url 2026-07-26-git-branch-strategy-issue-pr-merge %})에서 다뤘습니다.

### 5-4. 코드 주석과 docstring

**작성 시점** — 코드를 쓰는 그 순간. 나중은 없습니다.

**왜 필요한가** — 주석은 **코드가 스스로 말하지 못하는 것만** 적는 문서입니다.

- **적지 말 것**: `// 사용자 이름을 가져온다` 같은 코드의 번역. 코드를 읽으면 알 수 있는 내용을 적으면, 코드가 바뀔 때 주석이 거짓말이 됩니다.
- **반드시 적을 것**: 이상해 보이지만 이유가 있는 코드. `// 결제사 API가 간헐적으로 200과 함께 빈 바디를 반환해서 3회 재시도 필요 (2026-05 장애 #412)`

주석은 **What이 아니라 Why**입니다. 공개 API·라이브러리라면 docstring으로 인자·반환값·예외를 적어두면 IDE 자동완성과 문서 생성기가 그대로 활용합니다.

## 6. 검증 단계 — 다 됐다는 걸 어떻게 확인하는가

### 6-1. 테스트 계획서 / 테스트 케이스

**작성 시점** — 요구사항 확정 직후. **구현과 병렬로** 작성합니다. (구현이 끝난 뒤 쓰면 "구현된 대로"를 정답으로 삼게 되어 검증 의미가 사라집니다)

**담을 내용** — 테스트 범위와 제외 대상, 테스트 유형별 책임(단위/통합/E2E/성능/보안), 테스트 환경과 데이터, 케이스별 사전조건·절차·기대결과, 합격 기준과 결함 심각도 분류, 회귀 테스트 대상.

**왜 필요한가** — 테스트 케이스는 **요구사항을 검증 가능한 형태로 번역한 것**입니다. 요구사항 하나가 테스트 케이스로 옮겨지지 않는다면 그 요구사항은 애초에 검증 불가능하게 쓰인 것입니다. 즉 테스트 계획서 작성은 **요구사항 품질 검사**를 겸합니다.

### 6-2. 릴리스 체크리스트

**작성 시점** — 첫 배포 직전. 그리고 **사고가 날 때마다 항목이 늘어납니다.**

**담을 내용** — 배포 전 확인(마이그레이션 순서, 환경변수, 피처 플래그, 의존 서비스 배포 순서), 배포 후 확인(헬스체크, 핵심 지표 대시보드, 에러율), 롤백 절차와 판단 기준.

**왜 필요한가** — 배포는 긴장 상태에서 수행되고, 긴장하면 아는 것도 빼먹습니다. 체크리스트는 항공기 조종사가 쓰는 것과 같은 이유로 존재합니다. **모든 항목에는 "이걸 빼먹어서 사고 났던 날"이 하나씩 있어야** 합니다. 없는 항목은 삭제해도 됩니다.

## 7. 배포·운영 단계 — 어떻게 굴리고 고치는가

### 7-1. CHANGELOG와 릴리스 노트 (둘은 다릅니다)

| 구분 | CHANGELOG | 릴리스 노트 |
|---|---|---|
| 독자 | 개발자 | 사용자·고객 |
| 범위 | 모든 변경 사항 | 사용자에게 의미 있는 변경만 |
| 문체 | 기술적, 간결 | 설명적, 이점 중심 |
| 형식 | 버전별 목록 | 하이라이트 + 스크린샷 |

**담을 내용 (CHANGELOG)** — 버전과 날짜, `Added / Changed / Deprecated / Removed / Fixed / Security` 분류, 그리고 **Breaking Change와 마이그레이션 방법**.

**왜 필요한가** — 라이브러리를 올릴 때 우리가 확인하는 것은 코드가 아니라 CHANGELOG입니다. 여기에 유의적 버전(Semantic Versioning, `MAJOR.MINOR.PATCH`)을 결합하면 — 호환성을 깨면 MAJOR, 하위 호환 기능 추가는 MINOR, 버그 수정은 PATCH — 사용자가 **버전 번호만 보고 업그레이드 위험도를 판단**할 수 있게 됩니다. 이건 문서가 제공하는 가장 실용적인 가치 중 하나입니다.

### 7-2. 런북 (Runbook / Playbook)

**작성 시점** — 서비스를 운영에 올리기 전. 그리고 **장애가 날 때마다 갱신**.
**주 작성자** — 해당 서비스를 운영하는 개발자.

**담을 내용**

- 서비스 개요, 아키텍처 요약, 의존 서비스
- **알림(Alert)별 대응 절차** — "이 알림이 오면 무엇을 확인하고, 무엇을 실행하는가"
- 실제로 복사해서 붙여넣을 수 있는 명령어와 쿼리
- 대시보드·로그·모니터링 콘솔 **직접 링크**
- 에스컬레이션 경로: 언제, 누구에게

**왜 필요한가** — 런북의 목적은 **"당직자가 담당자를 깨우지 않고 스스로 복구하게 하는 것"** 입니다. 그래서 런북에는 몇 가지 강한 제약이 있습니다.

- **알림에서 링크로 바로 연결되어야 한다.** 위키 어딘가에 있는 긴 문서는 장애 중에 아무도 찾지 못합니다.
- **짧아야 한다.** 배경 설명은 평시 문서로 빼고, 런북에는 절차만 남깁니다.
- **주기적으로 실행 검증해야 한다.** 명령어가 낡은 런북은 없느니만 못합니다. 실제 장애 때 실행했다가 실패하면 대응 시간을 두 배로 잡아먹습니다.

### 7-3. 장애 회고 (Postmortem)

**작성 시점** — 장애 복구 후 24~72시간 이내. 기억이 살아있고 로그가 남아있을 때.

**담을 내용**

- 요약: 무슨 일이 있었고, 영향 범위(사용자 수·시간·금액)는 얼마인가
- **타임라인**: 발생 → 감지 → 인지 → 조치 → 복구 시각과 각 시점의 행동
- 근본 원인 분석 (5 Whys 등)
- 잘 대응된 점 / 운이 좋았던 점 / 아쉬웠던 점
- **담당자와 기한이 명시된 후속 조치 항목**

**왜 필요한가** — 회고의 목적은 원인 규명이 아니라 **재발 방지**입니다. 그래서 두 가지가 결정적입니다.

첫째, **비난하지 않는(blameless) 문화.** "누가 잘못했나"를 묻는 순간 사람들은 사실을 축소해서 보고하고, 그러면 진짜 원인에 도달할 수 없습니다. Google SRE가 강조하는 원칙도 이것입니다. 한 사람의 실수로 서비스가 멈췄다면, 문제는 그 사람이 아니라 **한 사람의 실수로 서비스가 멈출 수 있는 시스템**입니다.

둘째, **후속 조치 추적.** 담당자와 기한 없이 "모니터링을 강화하자"로 끝난 회고는 다음 달 같은 장애로 돌아옵니다. 후속 조치는 반드시 이슈로 등록해서 일반 업무처럼 관리해야 합니다.

### 7-4. 온보딩 문서

**작성 시점** — 새 팀원이 합류할 때마다 **그 사람이 직접 갱신**하게 하는 방식이 가장 효과적입니다.

**담을 내용** — 첫 주 체크리스트, 계정·권한 신청 목록, 시스템 전체 지도, 용어집, 팀 일하는 방식(스프린트, 배포 주기, 회의체), 자주 묻는 질문.

**왜 필요한가** — 온보딩 문서는 **가장 빨리 낡고, 가장 검증하기 쉬운 문서**입니다. 신규 입사자가 막힌 지점이 곧 문서의 결함 목록이고, 그 사람이 아직 "모르는 상태"일 때만 그 결함이 보입니다. 이 기회를 놓치면 문서는 다음 입사자까지 그대로 낡아 있습니다.

## 8. 사용자 문서 — Diátaxis 프레임워크

외부 사용자나 다른 팀이 쓰는 제품·라이브러리라면 사용자 문서가 필요합니다. 여기서 유용한 것이 Daniele Procida가 제안한 **Diátaxis** 프레임워크입니다. Django, Cloudflare, Canonical 등이 채택하고 있습니다.

![Diátaxis의 네 가지 문서 유형 사분면](/assets/images/diataxis-quadrants.png)

*Diátaxis 공식 다이어그램. 세로축은 Action(실행) ↔ Cognition(인지), 가로축은 Acquisition(습득) ↔ Application(적용)입니다. 각 유형 아래 주황색으로 적힌 단어가 그 문서가 채워주는 사용자의 필요입니다 — 튜토리얼은 배움(learning), How-to는 목표 달성(goals), 설명은 이해(understanding), 레퍼런스는 정보(information). (출처: [Daniele Procida, diataxis.fr](https://diataxis.fr/), CC BY-SA 4.0)*

| 유형 | 목적 | 사용자 상태 | 예시 |
|---|---|---|---|
| **튜토리얼** | 배우게 한다 | 아무것도 모름 | "5분 만에 첫 API 호출하기" |
| **How-to 가이드** | 문제를 해결한다 | 이미 알고, 일하는 중 | "OAuth 로그인 연동하는 법" |
| **레퍼런스** | 사실을 찾게 한다 | 정확한 정보가 필요 | API 레퍼런스, 설정 옵션 표 |
| **설명(Explanation)** | 이해시킨다 | 맥락이 궁금함 | "우리가 이벤트 기반을 택한 이유" |

두 축으로 보면 명확합니다. 위쪽 절반은 **무언가를 하는(action)** 문서, 아래쪽 절반은 **무언가를 아는(cognition)** 문서입니다. 그리고 왼쪽 절반은 **배우는 중(acquisition)** 인 사람을, 오른쪽 절반은 **일하는 중(application)** 인 사람을 위한 문서입니다. 튜토리얼은 실행+습득, How-to는 실행+적용, 설명은 인지+습득, 레퍼런스는 인지+적용에 놓입니다.

**가장 흔한 실수는 한 페이지에서 유형을 섞는 것입니다.** 처음 따라 하는 사람을 위한 튜토리얼 중간에 내부 동작 원리 설명이 3문단 들어가면, 배우려는 사람은 흐름이 끊기고 이해하려는 사람은 원하는 깊이를 얻지 못합니다. 둘 다 실패합니다. **한 문서는 한 가지 역할만** 하고, 나머지는 링크로 연결하세요.

## 9. 프로젝트 규모별 최소 세트

모든 문서를 쓸 필요는 없습니다. 규모별로 "여기까지"를 정해두는 편이 현실적입니다.

![프로젝트 규모별 개발 문서 최소 세트](/assets/images/doc-set-by-scale.jpeg)

*안쪽 상자는 바깥 상자에 그대로 포함됩니다. 가장 안쪽의 세 개(README·ADR·장애 회고)는 혼자 하는 프로젝트에서도 없으면 시간이 지날수록 손해가 커지는 문서이고, 바깥으로 갈수록 조직이 커져야 비로소 값어치를 하는 문서들입니다. 조직이 크다고 안쪽 문서를 건너뛰는 게 아니라, 안쪽 위에 쌓는 것입니다.*

| 문서 | 1인 토이 프로젝트 | 소규모 팀 (2~8명) | 중대형 / 다팀 |
|---|---|---|---|
| README | 필수 | 필수 | 필수 |
| ADR | 권장 | **필수** | 필수 |
| PRD / 요구사항 | 생략 | 간이 (1페이지) | 필수 |
| 설계 문서 | 생략 | 큰 기능만 | 필수 |
| RFC | 생략 | 생략 | 필수 |
| API 명세 | 생략 | **필수** | 필수 |
| CONTRIBUTING·컨벤션 | 생략 | 필수 | 필수 |
| 테스트 계획서 | 생략 | 간이 체크리스트 | 필수 |
| CHANGELOG | 권장 | 필수 | 필수 |
| 런북 | 생략 | 운영 서비스면 필수 | 필수 |
| 장애 회고 | 생략 | **필수** | 필수 |
| 온보딩 문서 | 생략 | 권장 | 필수 |

정말 아무것도 못 쓰겠다면 **딱 세 개만 쓰세요.**

1. **README** — 남이 실행할 수 있게
2. **ADR** — 중요한 결정의 이유를 남기게
3. **장애 회고** — 같은 사고를 반복하지 않게

이 셋은 공통점이 있습니다. **없을 때 손해가 시간이 지날수록 커진다**는 것입니다. 반대로 PRD나 설계 문서는 프로젝트가 끝나면 가치가 급감합니다.

## 10. 문서가 썩지 않게 하는 법 — Docs as Code

문서화 실패의 대부분은 "안 써서"가 아니라 **"쓰고 방치해서"** 발생합니다. 문서 부패의 근본 원인은 명확합니다. **문서가 코드와 분리되어 있기 때문**입니다. 코드를 고치는 사람과 문서가 있는 곳이 멀수록 갱신되지 않습니다.

해법은 **문서를 코드처럼 다루는 것(Docs as Code)** 입니다.

1. **같은 저장소, 같은 PR** — 문서를 마크다운으로 코드 옆에 두면, API를 바꾼 PR에서 리뷰어가 "명세도 같이 고쳐주세요"라고 말할 수 있습니다. 위키에 있으면 아무도 그 말을 못 합니다.
2. **단일 출처(Single Source of Truth)** — 같은 내용을 두 곳에 적으면 반드시 한쪽이 틀려집니다. 복사 대신 **링크**하세요.
3. **가능한 것은 자동 생성** — OpenAPI 스펙에서 API 문서, 코드에서 docstring 문서, 커밋에서 CHANGELOG. 사람이 손으로 옮겨 적는 구간이 곧 부패 지점입니다.
4. **문서 갱신을 완료 조건(DoD)에 넣기** — "코드 + 테스트 + 문서"가 끝나야 완료입니다. PR 템플릿에 `[ ] 관련 문서를 갱신했다` 체크박스 한 줄이면 됩니다.
5. **소유자와 갱신일 명시** — 문서 상단에 `최종 검토: 2026-08-02 / 담당: @xxx`. 6개월 넘은 문서는 검토 대상으로 자동 표시하는 것도 방법입니다.
6. **과감하게 삭제하기** — 틀린 문서는 없는 문서보다 나쁩니다. 없으면 물어보기라도 하지만, 틀린 문서는 사람을 잘못된 길로 확신을 갖고 데려갑니다. 유지할 수 없는 문서는 지우세요.

## 11. 정리

- **문서는 많이 쓰는 게 아니라, 틀리면 손해가 큰 것을 결정이 굳는 시점에 쓰는 것**입니다.
- **기획**은 PRD(사용자가 원하는 것)와 SRS(시스템이 해야 하는 것). 범위 밖과 비기능 요구사항이 진짜 가치입니다.
- **설계**는 Design Doc(어떻게 만들지) / RFC(합의) / ADR(왜 그렇게 정했는지). 셋 중 하나만 고른다면 가장 짧고 가장 오래 사는 **ADR**입니다.
- **API 명세**는 팀 간 계약서이자 코드·목·테스트를 파생시키는 원본입니다.
- **구현**의 README는 "남이 혼자 실행할 수 있는가"가 유일한 합격 기준. 주석은 What이 아니라 **Why**.
- **운영**의 런북은 짧고 알림에서 바로 링크되어야 하고, 장애 회고는 **비난 없이 + 담당자와 기한이 있는 후속 조치**로 끝나야 합니다.
- **사용자 문서**는 Diátaxis 4분류를 한 페이지에 섞지 마세요.
- 문서가 썩는 이유는 코드와 떨어져 있기 때문입니다. **같은 저장소, 같은 PR, 자동 생성, 그리고 과감한 삭제.**

결국 좋은 문서는 분량이 아니라 **"다음 사람이 물어보지 않아도 되게 만드는가"** 로 평가됩니다. 지금 팀에서 가장 자주 반복되는 질문이 무엇인지 떠올려 보세요. 그 질문의 답을 적는 것이 지금 가장 필요한 문서입니다.
